# D26 — The portals are Next.js App Router and TypeScript, with no UI kit, no state library and the prototype's own stylesheet as the design system

_9 Sep 2026 · §23 · STAGE-1 §1.1 · closes a gap the documents left open_

STAGE-1 §1.1 decided TypeScript and forbade the additions — *a UI kit, a state library, an ORM, a component library, a mono-repo tool with its own opinions, a linter config that argues with the one already there* — but **no document named a framework.** A 8 Sep session line mentions "the existing TypeScript/Next.js/Fastify stack already set in `docs/DECISIONS.md`"; it is not there. This closes that gap rather than leaving the next session to re-derive it from the code, which `CLAUDE.md` forbids.

**Next.js 15, App Router, React 19, TypeScript strict.** Chosen over a plain Vite SPA because week 1 needs a server the same application already owns: the Zoho OAuth authorisation-code callback (1.3), the write path that writes Zoho as the signed-in person and the mirror from Zoho's answer *in the same request* (1.4), and the read routes whose scoping must be enforced in the backend and not by a hidden button (1.5, D24). A client-only SPA would need a second service for those on day one; this way `console/` and `portal/` are each one deployable, and `db-*/functions/` keeps only what §23 puts there — the webhook receivers and the jobs.

**Nothing else is added.** No UI kit, no component library, no state library, no CSS framework, no icon package, no date library, no chart library. State is one React context and one `useReducer` whose cases carry the prototype's own mutator names; the clock is the one function rule 9 requires, frozen for the fixtures and never `new Date()` at render; charts and meters are the CSS the prototype already draws them with. The dependency list is `next`, `react`, `react-dom` and the types.

**`console/prototype/ir-console.html`'s `<style>` block is the design system, copied verbatim to `console/src/app/console.css`.** It is not re-authored, not converted to CSS Modules and not replaced by utility classes. It already carries the tokens, both themes, the eight categorical slots and the mobile breakpoint that leaves the desktop layout exactly as it is — so a verbatim copy is what makes "built to match the prototype, not re-designed" (STAGE-2, *Design*) checkable rather than a matter of opinion. **The consequence to hold:** a change to that file is a design change and belongs in `docs/design-spec.html` first. Where the prototype and the Build Book disagree the Build Book still wins, and the stale picture is said out loud rather than quietly followed.
