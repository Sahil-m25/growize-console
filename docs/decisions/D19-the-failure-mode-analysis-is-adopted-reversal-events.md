# D19 — The failure-mode analysis is adopted: reversal events, one actor per consequence, delegation everywhere, a KYC step, recording always allowed, an allow-list mapper, a real job runner, a heartbeat that lives elsewhere — and eleven canaries in place of the six alerts

_5 Sep 2026 · §22 · register segment F_

Added 5 Sep 2026 after two independent reads of v1.2 found 145 failure modes, 27 near-certain and 53 silent, of which the six alerts of §15 saw eleven in time (§22). **Why:** five patterns explain most of the register — gates that only open, two actors per consequence, one named person everywhere, watchers that watch themselves, and a reconcile that compares records while the failures live between them — and each pattern has one structural answer. **Rejected:** keeping the six alerts and adding rows to the reconcile (a record-level diff cannot see a dropped transition or a duplicate link); a second monitor inside the same project (it dies with the cron it watches); trusting eMudhra’s callback or Zoho’s webhook payload as fact (both are hints; the record is re-fetched). **Cost:** three more events, a migration phase, a second provider for the heartbeat, PITR on the leads project, a weekly statement import, and the one exception to D8 — signed instruments copied to S3 at signing.
